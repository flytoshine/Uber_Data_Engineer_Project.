# Uber Data Engineering — Real-Time Lakehouse Pipeline

An end-to-end **Uber-style ride data engineering project** built on Microsoft Azure and Databricks.

The project simulates a production-like ride platform where **live ride events** are generated by a FastAPI web application, routed through Azure Data Factory and Azure Event Hubs, processed with **Spark Structured Streaming / Spark Declarative Pipelines**, and transformed into analytics-ready **Star Schema** data models.

It also uses GitHub-hosted reference data as an internal/static API source for mapping datasets such as cities, payment methods, ride statuses, vehicle types, vehicle makes, and cancellation reasons.

## Data Flow

### 1. Live ride event generation

A lightweight **FastAPI web application** acts as the simulated ride-producing application. Each generated ride represents a real-time event such as a booking, passenger, driver, vehicle, payment, location, fare, rating, and ride status.

The objective is to reproduce the shape of a real streaming data source without depending on an external Uber API.

### 2. Azure Data Factory

**Azure Data Factory (ADF)** is used as the orchestration layer between the source systems and the Azure data platform.

ADF coordinates ingestion for both:

- Live ride/event data
- Static/reference mapping data

### 3. Azure Event Hubs

Live ride events are published to **Azure Event Hubs**.

Databricks consumes Event Hubs through its Kafka-compatible endpoint using Spark Structured Streaming.

The streaming configuration supports:

- Continuous event consumption
- Starting offsets
- Batch limits with `maxOffsetsPerTrigger`
- Watermark-based processing downstream
- Checkpointing through the Databricks pipeline

### 4. GitHub reference data

GitHub is used as a simple internal/static source for reference datasets used to enrich ride events.

Examples include:

- Cities
- Payment methods
- Ride statuses
- Vehicle makes
- Vehicle types
- Cancellation reasons

These datasets provide the descriptive attributes required to turn coded IDs in the ride stream into business-friendly information.

### 5. Bronze layer

The Bronze layer keeps ingestion close to the source structure.

The streaming ingestion logic is implemented with Spark's `pyspark.pipelines` API and reads Event Hubs through the Kafka interface.

The main raw stream is represented by:

```text
rides_raw
```

Reference datasets are also landed as Delta tables under the Bronze layer.

### 6. Silver layer — One Big Table

The Silver layer creates a denormalized **One Big Table (OBT)** from the ride stream and reference data.

The current transformation joins the ride stream with mapping tables for:

- Vehicle make
- Vehicle type
- Cancellation reason
- City
- Payment method
- Ride status

The resulting dataset is:

```text
silver_obt
```

A **3-minute watermark** is applied to the booking timestamp to help manage late-arriving streaming events.

### 7. Gold layer — Star Schema

The Gold layer converts the denormalized Silver dataset into an analytics-friendly **Star Schema**.

The model contains dimension tables for entities such as:

```text
Dim Passenger
Dim Driver
Dim Vehicle
Dim Payment
Dim Booking
Dim Location
```

and a central:

```text
Fact Ride
```

The fact table contains ride-level measures and foreign-key style references to the dimensions.

## Change Data Capture & SCD

The Gold layer uses Databricks pipeline CDC functionality with `create_auto_cdc_flow`.

The project demonstrates both:

### SCD Type 1

Used for dimensions where the latest value is sufficient, such as:

- Passenger
- Driver
- Vehicle
- Payment
- Booking

### SCD Type 2

Used for **Location** so historical changes to location attributes can be retained.

The location dimension uses the update timestamp as the sequencing column.

## Streaming Design Considerations

This project demonstrates several important real-time data engineering patterns:

**Event-driven ingestion** — ride events enter the platform continuously rather than as a single batch load.

**Watermarking** — a 3-minute watermark is applied to the booking timestamp to handle late-arriving events.

**Reference-data enrichment** — coded streaming records are enriched with descriptive static datasets before reaching the Gold layer.

**Deduplication** — dimension views use key-based deduplication before CDC processing.

**CDC-driven dimensions** — Auto CDC flows maintain target dimension tables and support SCD Type 1 and Type 2 behavior.

**Medallion architecture** — Bronze, Silver, and Gold layers separate ingestion, transformation, and analytical consumption.

## Key Engineering Decisions

### Why One Big Table in Silver?

The Silver OBT provides a convenient, enriched analytical intermediate layer. It centralizes the joins between the streaming ride record and reference entities before the data is separated into dimensional structures.

### Why Star Schema in Gold?

The Star Schema creates a stable analytical model where business users and BI tools can query ride facts while slicing the data by passenger, driver, vehicle, payment, booking, and location dimensions.

### Why SCD Type 1 and Type 2?

Different dimensions have different historical requirements. Type 1 keeps the current state where history is not required, while Type 2 preserves changes over time when historical reporting matters.

## Security Note

**Do not commit Azure Event Hubs connection strings, SAS tokens, storage account keys, or signed Blob URLs to GitHub.**

The pipeline code is designed to read the Event Hubs connection string from Databricks configuration/secrets, for example:

```python
EH_CONN_STR = spark.conf.get("connection_string")
```

Before making this repository public, remove or rotate any credentials or SAS URLs that may have existed in development notebooks/scripts and replace them with Databricks Secrets, Key Vault, environment variables, or another secure secret-management mechanism.
